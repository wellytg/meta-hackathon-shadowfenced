# T62 — Explain the rules: what each protection catches, why, and which rule fired

Users can open Settings → Rules, but the panel lists only the policy.yaml codenames and clients plus custom rules. It
never says what Shadowfenced protects as a whole (keys, personal data, card numbers, bank details, health details,
re-identification, person searches) or why. The risk card says what was done but not which rule fired or why that rule
exists. Read `static/rules.js`, `static/app.js` (risk card), `tier1.py` (detectors), `reid.py`, `person_search.py`,
`docclass.py`, `engine.py`, `policy.yaml`, `docs/UI_STATES.md`.

## 1. One rule catalogue, generated from what the code really does
Add `src/shadowfenced/rule_catalog.py`: a list of entries, one per protection that EXISTS in the code today. Each entry:
`id`, `title` (plain words), `catches` (one line, e.g. "API keys and tokens for OpenAI, Anthropic, AWS and others,
including base64-encoded ones"), `action` (BLOCK/REDACT/WARN/HOLD, read from policy/engine, not hard-coded twice),
`can_send_anyway` (from `user_can_keep`), `why` (2 sentences, plain words), `related` (list of short framework notes,
see below), `detectors` (the internal detector/check names it covers, e.g. `tier1.key_scan`, `reid`,
`person_search`). Serve it at `GET /api/rules/catalog`. Tests must fail if an entry names a detector that does not
exist, and if a detector in the trace (`tier1.*` steps, reid, person search, contract, image, audio) has no entry.
Do not add entries for protections that do not exist.

Framework notes (`related`) must be accurate and modest — they explain why the data is sensitive, they do not claim
compliance. Use only these where they genuinely apply:
- Personal data (names, emails, phones, addresses, dates of birth): "GDPR / UK GDPR treat this as personal data";
  "CCPA/CPRA (California) treat it as personal information".
- Payment card numbers: "PCI DSS: card numbers must be protected wherever they are stored or sent".
- Bank accounts, routing, IBAN, SWIFT: "GLBA (US) protects customers' non-public financial information".
- Health details (only if the code detects them, e.g. via `docclass`/sensitivity cues): "HIPAA (US) protects health
  information that can be tied to a person; GDPR treats health data as a special category".
- Re-identification (combinations): "Name, date of birth and postcode together can identify most people, even with no
  single 'secret' field" (no statistics unless already cited in the repo).
- Keys and secrets: "Security practice: a leaked key gives anyone the account's access; it cannot be un-sent".
- Person search: "Looking up a private person can expose them to stalking or harassment; GDPR covers processing
  someone else's personal data".
Footer text on the panel: "These notes explain why the data is sensitive. They are not legal advice and Shadowfenced
does not make you compliant with any law."

## 2. Rules panel shows "What Shadowfenced protects"
At the top of the Rules panel, before Built-in/Custom, add a section "What Shadowfenced protects" listing the catalogue:
title, action badge, one-line `catches`; click/expand shows `why`, `related` notes and "You can send anyway: yes/no".
Keep the existing Built-in (codenames, clients), Custom and Add-a-rule sections and say above Built-in: "Your
organisation's own words (from policy.yaml)". Also fix: the panel's title row sits under the public-demo banner when
hosted (top cut off) — offset it like the header.

## 3. Every risk card names the rule that fired
Add a line to the risk card and the details drawer: "RULE  <catalogue title> · Why this rule" where "Why this rule"
expands the catalogue `why` + `related` inline and links to the Rules panel entry. The server decision already has
reasons/trace; map them to catalogue ids on the server (`rule_ids` on the decision payload) so the UI never guesses.

## 4. Person searches: "this may be you"
When the person-search check fires (name + date of birth or other identifying details, subject not public), the WARN
card reads:
- Title: "Searching for a person"
- Why: "This message names a person and gives details that identify them (<labels only, never values>)."
- A short block: "If this is you: it's your choice — you can send it. If it's someone else: the AI provider receives
  their details, the request may be logged, and looking up a private person can expose them to harm. Rule: Person
  search."
- Buttons as today (Generalise · Send anyway · Cancel); "Send anyway" label stays.
Keep values out of every reason, banner and log line (labels only). Historical/public figures keep today's behaviour
(T48).

## 5. Tests
Catalogue/detector coverage both ways (above); `/api/rules/catalog` shape; every catalogue entry has non-empty `why`
and the footer disclaimer is present in the UI; a key send returns `rule_ids` containing the key rule; a person
search with name + DOB returns the person-search rule and the "If this is you" text, with no message values in the
payload reasons; hosted Rules panel title not covered (CSS check). Classic Windows 3.11 look. Run
`python -m pytest -q -p no:cacheprovider` and `python scripts/ci.py`. Do not commit.
