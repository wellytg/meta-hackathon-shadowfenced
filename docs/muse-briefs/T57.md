# T57 — Background Glimmer review: the card must show "checking" and then resolve

Live test on the combined build: "Summarise the life of Ada Lovelace, born 10 December 1815 in London." The word
"born" is a sensitivity cue, so `/api/send` returns HOLD with reason "sensitivity cue word needs Glimmer review -> HOLD"
and Muse Glimmer reviews it in the background; about 10–20 s later the hold is `released`, the receipt becomes
"Sent clean", the line "GLIMMER CHECKED IT: NOTHING SENSITIVE. SENT." appears and the answer arrives. That part works.

What is wrong on screen (read `static/app.js` risk-card and hold code, `docs/UI_STATES.md`):
1. While the review runs, the risk card shows the HOLD layout: "SENDING (nothing left to send)", "WHY IT'S RISKY A
   possible pointer to sensitive data needs review." and "WHAT WAS DONE Waiting for you: Generalise · Send anyway ·
   Cancel" — but nothing is waiting for the user. For a cue-word background review show a compact card: title
   "CHECKING", Sending = the message text, Why = "Contains a word that can point to personal data ('born'); Muse Glimmer
   is checking it on this PC", What = "Checking… (Ns)". No choice buttons unless the review ends in a real HOLD that
   needs the person.
2. When the review releases the message, the card is replaced by the quiet receipt
   "✓ Checked by Muse Glimmer · nothing sensitive" (Why still available) and the details drawer decision changes from
   HOLD to the final decision. When the review ends in a real hold, the card switches to the normal HOLD card with its
   choices.
3. Name the cue word that fired (from the server reason if available; add it to the server reason in `engine.py` as
   `cue='born'` if it is not there yet) without echoing any other message text in the reason.
4. Tests: state-model tests for checking → released → quiet receipt, checking → real hold → HOLD card; server reason
   includes the cue word. Run `python -m pytest -q -p no:cacheprovider`. Do not commit.
