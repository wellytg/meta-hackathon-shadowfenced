# T38b — Square Windows 3.11 style kept; make every control work state by state

The owner's direction: keep the deliberate old-school Windows 3.11 / DOS look (square boxes, hard 2px outlines, paper
background, ink text, safety orange for blocked, steel blue for allowed, amber for review). Your previous round made
the composer rounded: make all corners square again (radius 0 everywhere except where the browser forces otherwise).
Function matters more than decoration now. `docs/muse-briefs/_ui_review_reference.md` describes how a reviewer will
judge the screen; use it as a checklist.

1. Write `docs/UI_STATES.md`: for every interactive element (composer, Send, Attach, microphone, model picker,
   provider cards, settings menu items, rules drawer, descriptive mode, receipts and their Why, hold/review card,
   Generalise and Send-anyway choices, details drawer, log viewer, pairing token, chat list, New chat, Jump to latest)
   list each state (idle, hover/focus, busy, success, error, disabled) and what the user sees and can do, following
   the common behaviour of ChatGPT, Claude, Gemini and Grok. Then make the code match it.
2. Specific behaviours to guarantee: Enter sends, Shift+Enter newline; Send disabled while empty or while a request is
   in flight, with a visible "Checking locally…" state; the typed text is kept if a request fails; microphone: idle →
   (first time) consent → "Listening 0:07" with a Stop control → "Transcribing…" → text inserted at the cursor →
   underlines appear; errors appear on one line inside the composer next to the control that failed and clear on the
   next action; receipts always show a text label, never colour alone; the newest turn stays in view unless the user
   scrolled up; keyboard can reach every control in a sensible order, Escape closes panels.
3. Keep every id and `data-testid`. Add tests for the state model where possible (pure functions in app.js exported
   for tests via a small harness, or static checks). Run `python -m pytest -q`. Do not commit.
