# T82 — Security policy, disclaimer, contributing, and beyond the hackathon

Docs only. Do NOT edit README.md, `src/`, or `tests/` (other branches are editing them). Do not commit; leave
changes in the working tree and print a summary. Plain English, short sentences, no hype, no marketing words.
Facts must match the repo (read README.md, `docs/results/`, `docs/FINETUNE.md`, `setup/README.md`,
`extension/README.md`).

## Write
1. `SECURITY.md` (repo root):
   - **Use at your own risk.** Shadowfenced is a hackathon build. It has been tested (1,100+ tests, a sealed
     evaluation set, a red-team test folder, an independent review on Nov 4), but it is not audited. Most of the
     code was written by an AI coding agent (Muse Code) from task briefs that were planned with AI and steered
     by a person; briefs and code can contain mistakes. Do not rely on it as your only control for real
     secrets or regulated data. Provided as is, under the repo LICENSE.
   - Supported version: `main` / release `v1.0-hackathon`.
   - How to report a vulnerability: open a GitHub security advisory (private report) on the repo; do not post
     working exploits in public issues. What to include.
   - Browser extension notes: it talks only to the local app on 127.0.0.1:8765 with a pairing token; it is
     loaded unpacked (not store-reviewed); page scripts on an AI site can read what you type before the
     extension acts (a limit of any in-page guard); review the code before loading it.
   - Pointers: `docs/security/` (threat model, red-team results, Nov 4 review — some files arrive in parallel
     branches; link the folder, not specific files).
2. `CONTRIBUTING.md`: welcome testing and contributions; how to run tests (`setup/AGENT_SETUP.md` command);
   synthetic data only, never real keys (the repo guard test fails on key shapes); one change per PR with
   tests; good first areas: new detectors, DOCX parts, more AI sites in the extension, red-team cases.
3. `docs/ROADMAP.md` — "Beyond the hackathon". Shadowfenced was built for the Meta Global AI Developer
   Hackathon, and the problem is real: people want to use AI without leaking what they work on. Sections:
   - **Small local judges for machines without a GPU:** most PCs have no 12 GB GPU. The Nov 4 experiment
     trained Llama 3.2 3B (QLoRA) as a judge: on the sealed set, 23/26 sensitive caught and 2/14 harmless
     flagged at 3.5 s, vs Glimmer 25/26 and 13/14 at 7.3 s (README). Next: quantized 1B–3B judges (4-bit GGUF
     via Ollama), CPU-only latency targets, more near-miss training rows for its 3 misses, measured inside the
     full pipeline.
   - **How well do local models protect their own host?** A test plan: which local models resist prompt
     injection aimed at the judge; leak rate vs size and quantization; CPU vs GPU latency; a public benchmark
     built from the synthetic sets.
   - **Hardening** before real use (link `docs/security/`): fixes from the Nov 4 review, DOCX parts, CSRF on
     the local console, extension answer restore.
   - **More places:** more AI sites in the extension, IDE agents, store-published extension.
   - **Community:** issues welcome, good first issues, how decisions are logged without storing text.
   Keep it to about one screen.
