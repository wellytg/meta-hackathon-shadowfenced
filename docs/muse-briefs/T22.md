# T22 — Agent gate: check every message and recognise protected keys

Files you own: the proxy path in `src/shadowfenced/app.py` (`extract_user_text`, `_forward_messages`,
`chat_completions` and helpers), a new `src/shadowfenced/keyguard.py`, `src/shadowfenced/config.py` (one new
setting), and new tests. Do not change the web UI or the behaviour of `/api/scan` and `/api/send`.

1. `/v1/chat/completions` must gate every message role it forwards (system, user, assistant, tool) and assistant
   tool-call arguments, not only user messages, and must forward messages in their original order with their
   original roles. Redaction replaces only the sensitive spans inside each message. A BLOCK in any message blocks the
   request.
2. Protected keys. At startup read the variable names in `SF_PROTECT_KEYS` (default `META_API_KEY,MODEL_API_KEY`)
   from the existing settings source, and keep only an HMAC-SHA256 of each value under a random per-process salt:
   never the value itself, never logged. When any gated text contains one of these values, directly or in an
   encoding the canary decoder already handles (base64, hex, reversed, url, split), the request is BLOCKed as class
   `secret`, kind `protected_key`, with a reason naming the variable (for example "META_API_KEY appeared in a tool
   message").
3. The decision log entry for such a block records `protected_key: <variable name>`, the message role, and
   `left_machine: false`. Add `GET /api/keyguard` returning the protected variable names and how many times each was
   caught (no values).
4. Tests with fake values set through the settings env override: direct, base64 and split occurrences in a tool
   message are blocked; order and roles are preserved for clean requests; nothing in logs or responses contains the
   value. Run `python -m pytest -q` and report. Do not commit.
